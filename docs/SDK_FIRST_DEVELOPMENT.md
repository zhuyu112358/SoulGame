# SDK优先开发机制

> **核心原则**：开发任何新功能前，必须先检查Ember SDK和Arboreus SDK是否已有现成能力，优先复用而非重复造轮子。

## 一、为什么要SDK优先

1. **质量保障**：引擎SDK经过完整测试（Ember 2000+测试，Arboreus 1800+测试），比临时实现更可靠
2. **能力更强**：Ember有158个认知子系统，Arboreus有完整的世界模拟能力，远超游戏层临时实现
3. **维护成本低**：SDK升级时自动获得能力提升，不需要游戏层同步维护
4. **架构清晰**：游戏层专注玩法和表现，引擎层专注核心模拟，职责分离
5. **性能更优**：SDK底层经过优化，比GDScript临时实现性能更好

## 三、开发流程（强制执行）

### 新功能开发前检查清单

每开发一个新功能，必须按以下顺序检查：

```
1. 【功能定义】明确要实现什么功能、输入输出是什么
2. 【Ember SDK检查】查看Ember SDK是否有相关能力
   - 读取 D:\Sojourn\ember\dist\sdk\SDK_README.md
   - 查看 D:\Sojourn\ember\dist\sdk\sdk-manifest.json
   - 检查是否有现成的API或模块可复用
3. 【Arboreus SDK检查】查看Arboreus SDK是否有相关能力
   - 读取 D:\Sojourn\arboreus\docs\SDK.md
   - 查看 D:\Sojourn\arboreus\docs\SDK_API.md
   - 检查是否有现成的API或模块可复用
4. 【决策】
   - SDK有现成能力 → 必须使用SDK，在DEVLOG记录"[SDK复用]"
   - SDK有类似能力但需扩展 → 优先扩展SDK接口，而非游戏层绕过
   - SDK完全没有 → 游戏层实现，但在DEVLOG记录"[SDK缺失]"，并反馈给引擎团队
5. 【实现】按决策结果实现
6. 【验证】测试SDK集成是否正常，降级机制是否生效
```

### DEVLOG记录规范

每轮DEVLOG必须包含SDK使用情况：

```markdown
## SDK使用情况
- 本轮复用SDK能力：[列出复用的SDK API/模块]
- 本轮发现SDK缺失：[列出需要但SDK没有的能力，反馈给引擎]
- 本轮SDK集成问题：[列出集成中遇到的问题和解决方案]
```

## 四、当前战策SDK集成现状（待改进）

### 已有集成
- `platform/sdk/PlatformSDK.gd` - 平台SDK封装
- `config/sdk_versions.cfg` - SDK版本锁定配置
- `docs/SDK_INTEGRATION.md` - SDK集成指南

### 待改进项
1. **AI决策**：当前战策自己实现了SoulAIController，应评估是否可复用Ember的感知-决策-行动循环
2. **单位移动/寻路**：当前自己实现移动逻辑，应评估是否可复用Arboreus的路径规划
3. **碰撞检测**：当前自己实现障碍物碰撞，应评估是否可复用Arboreus的物理/碰撞系统
4. **灵魂属性/成长**：当前自己实现灵魂数据，应评估是否可复用Ember的灵魂数据结构
5. **事件系统**：当前自己实现信号/事件，应评估是否可复用Arboreus的事件总线

## 五、SDK版本升级流程

1. 引擎发布新SDK版本后，监控任务确认
2. 战策任务评估新版本的变更和影响
3. 更新 `config/sdk_versions.cfg` 中的版本号
4. 运行完整测试，验证兼容性
5. 如有破坏性变更，先适配再升级
6. 在DEVLOG记录SDK升级内容和影响

## 六、降级与容错

SDK调用必须有降级机制：
1. **超时降级**：SDK调用超时（5秒）后，使用游戏层本地实现
2. **不可用降级**：SDK服务不可用时，游戏仍可运行（使用本地模拟）
3. **错误重试**：SDK调用失败时，最多重试3次，然后降级
4. **状态记录**：记录SDK可用状态，在调试面板显示
